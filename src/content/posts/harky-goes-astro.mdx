TinaCMS is going default [Astro](https://tina.io/blog/astro-is-becoming-the-default-tinacms-starter) for their starter templates, so am I.

## Migration was cheap: TinaCMS is headless

**[TinaCMS](https://tina.io) is headless.** Your content is not locked in a database behind a vendor. It is MDX and JSON files sitting in your own GitHub repo, in `src/content/`.

So when I say I migrated the site, I mean I migrated the *UI Layer*. The content did not move. Not one file.

```
src/content/
  posts/
  poems/
  pages/
  tags/
  authors/
  global/
```

Those directories are byte for byte what they were on Next.js.

Tina reads them through a schema you define in `tina/`. The schema did not know it was talking to Next.js, and it does not know it is talking to Astro now. It just knows there is a collection called `post` with a title and a body.

That is the whole reason a framework migration on a content site is a weekend-shaped job instead of a quarter-shaped one. Most of the fear in a migration is about the content. Here the content was never at risk.

***

## Why TinaCMS is going Astro?

While I was looking into this, Matt Wicks published [Astro is becoming the default starter for TinaCMS](https://tina.io/blog/astro-is-becoming-the-default-tinacms-starter) on the TinaCMS blog.

Short version of his argument: more people are cloning the Astro starter than the Next.js one, Astro suits the things Tina users actually build like docs and blogs and marketing sites, and the newer visual editing uses data islands rather than hydrating the whole page as React.

He is also clear that the Next.js starter is not going away, so this is not a "move or else".

But it did tell me something useful. I was not making a lonely bet. The people who build the CMS are pointing the same direction.


Plus, I respect [Wicksy](https://www.ssw.com.au/people/matt-wicks/) (he is  undisputed leader of the Newy office & PO of TinaCMS)

## The strategy: branch, preview, merge

This is the part worth copying.

I did not rewrite in place. I did not touch main until the very end.

**1. New branch with the Tina Astro starter.**

I scaffolded [the Astro starter](https://github.com/tinacms/tina-astro-starter) onto a branch. The old Next.js `app/` and `components/` tree got parked out of the way rather than deleted, so I could still read it while porting.

**2. Prove one collection end to end before doing anything else.**

My first real commit on that branch did exactly one thing: render a single poem, and confirm that `/admin` could edit it live.

Not the whole site. One collection, all the way through, including the editing experience. If that had not worked, I would have stopped there and lost a day instead of a month.

**3. Port the rest in passes.**

Content parity first, then design, then the editorial pages. Each pass was its own commit, so when something broke I knew which pass broke it.

**4. Let Vercel preview the branch.**

This is the bit that made the whole thing low stress. Vercel builds a preview deployment for every branch, so the Astro version had a real URL, on real infrastructure, with real content, weeks before it went live.

I was not comparing a localhost to production. I was comparing two production builds.

**5. Merge, and let Vercel pick it up.**

When it was ready, I merged to main. Vercel did what it always does.

There was no cutover, no DNS change, no maintenance window. The deploy that shipped Astro looked exactly like every deploy before it.

## The one Vercel setting

Almost nothing changed on the Vercel side, which surprised me.

The one thing that did: **the framework preset.**

Vercel had the project pinned to Next.js. That is fine while main is Next.js, but it means the preview build for my Astro branch was being built as if it were Next.js, which does not work.

Changing the preset so the branch built as Astro was the whole infrastructure task. That plus the [`@astrojs/vercel`](https://docs.astro.build/en/guides/integrations-guide/vercel/) adapter in `astro.config.mjs`:

```js
export default defineConfig({
  output: 'static',
  adapter: vercel(),
});
```

`output: 'static'` is the line that matters. Every page is built once and served as a file.

I want to be careful here, because I had this wrong in my own head at first.

**Astro on Vercel can absolutely do ISR.** The adapter takes an `isr` option, with an expiration and a bypass token and the rest of it:

```js
adapter: vercel({ isr: { expiration: 60 } }),
```

I am just not using it. You can check this on your own build rather than take my word for it. Look in `.vercel/output/config.json` after a build. Mine has no `expiration` and no `isr` anywhere in it, and every page route resolves through Vercel's `filesystem` handler straight to prerendered HTML.

There is still one serverless function in my deploy, which did surprise me. It only handles the image endpoint, Astro's server islands, and Tina's editing route. No actual page touches it.

So the ISR problem did not go away because Astro cannot do ISR. It went away because I stopped asking for it.

## I used Claude for the template swap

I did not hand-port every component.

I pointed [Claude](https://claude.com/claude-code) at the old Next.js tree and the new Astro starter and had it do the translation, component by component, while I reviewed.

This is the kind of work AI is genuinely good at. It is mechanical, the target shape is well defined, and mistakes show up immediately because the page either renders or it does not.

It works well with Tina specifically because the schema is the contract. The agent is not guessing what a `post` looks like. It can read `tina/collections/post.ts` and see the fields.

The parts I did not delegate were the taste calls. Spacing, type, what to cut. An agent will happily port a component you should have deleted.

***

## The Cloudflare thing I did not do

I did look at moving to [Cloudflare](https://developers.cloudflare.com/pages/) at the same time.

Astro is arguably hosted better there. Static output on their edge is basically the ideal case for this kind of site, and I could see the argument.

I decided against it, and the reason is boring: it was not worth my time.

Vercel already supports Astro properly, my domains and previews and environment variables were already set up, and the whole point of this exercise was to have *less* to think about. Doing a framework migration and a host migration in the same move would have doubled the surface area for the same end result.

Maybe later. The site is static now, so if I ever do move, it will be a much smaller decision than it would have been on Next.js.

***

## The numbers

What actually changed, measured rather than guessed:

* Production dependencies went from **26 to 18**
* Dev dependencies went from **12 to 6**
* React and Next packages went from **12 to zero**
* JavaScript shipped to the browser went from a React runtime to **one 16 KB bundle**

That last one is the bit I like. The only JavaScript this site sends you now is the view-transitions router, so that navigating between pages does not flash.

Everything else is HTML that was built before you asked for it.

I have not run before and after Lighthouse numbers, so I am not going to pretend I have. Dependency counts and bundle size are what I actually measured.

***

## Was it worth it

For this site, yes.

Not because Next.js is bad. It is genuinely good at the thing it is for, which is applications. My blog is not an application. It is a pile of text with some pictures in it.

The honest summary is that I was using a framework built for a much harder problem than the one I had, and I only noticed when it sent me a bill.

If you are running Tina on Next.js and your site is mostly content, the migration is smaller than you think, and the reason is that your content is already portable. It is sitting in your repo in plain files. That was true the whole time.

Start with one collection on a branch. If that works, the rest is just typing.
